# Device provisioning and recovery

This document binds the operator workflow, local ESP32 setup portal, and first authenticated HTTPS request. It is separate from Sensor Protocol V1 because the local portal is not a public backend endpoint.

## Why SoftAP instead of Wi-Fi IBSS

On an unprovisioned ESP32-S3, the reference firmware starts a WPA2-protected Wi-Fi SoftAP named `OpenHACCP-<six hex digits>` and serves a local portal at `http://192.168.4.1`. SoftAP provides the direct device-to-phone/laptop experience commonly described as “ad hoc”, while remaining compatible with standard mobile Wi-Fi clients and captive-portal detection. It is not an Internet-facing access point.

The firmware uses simultaneous AP+STA mode only during setup. The WPA2 passphrase comes from `include/BuildSecrets.h`, must contain 8–63 characters, and must be unique per physical device or controlled production batch. Put that setup passphrase on the device label or inside its packaging; never commit it to Git. There is deliberately no universal production setup password.

## Operator workflow

1. Sign in at `/login` with a database-backed administrator or employee account.
2. Select the plus button next to **Geräte** and enter a device name, first measurement point, sensor type, location, temperature limits, and battery display thresholds. `device_uid` may be supplied or generated by the server.
3. The dashboard calls `POST /api/v1/dashboard/devices`. The backend creates the device, version-1 configuration, and measurement point in one database transaction.
4. Copy the one-time setup package. The 64-character device key is returned in this response only. The response uses `Cache-Control: no-store, private`; the database stores only its peppered HMAC-SHA-256 digest.
5. Power the unprovisioned sensor, join `OpenHACCP-…` using the setup passphrase from its label, and open `http://192.168.4.1`. Captive-portal detection also redirects common probe URLs to this page.
6. Enter the site’s 2.4-GHz Wi-Fi credentials and the complete setup package. The public API URL defaults to `https://haccp.pow24.org` but remains editable for another deployment whose certificate chains to the firmware’s embedded trust anchor.
7. The device joins the selected WLAN while keeping the setup AP available, synchronizes UTC, validates the server certificate chain and hostname, and performs an authenticated `GET /api/v1/device/config`.
8. Only after all checks pass does the firmware persist runtime configuration and finally mark the provisioning record ready. It then confirms success, reboots, and disables the setup AP.

If the browser is closed before the setup package is copied, the plaintext device key cannot be recovered. Rotate the device key with the existing CLI command or disable the incomplete device and create a new one.

## Local portal fields

| Field | Constraint | Stored on device |
|---|---|---|
| Wi-Fi SSID | 1–32 characters | yes |
| Wi-Fi password | 0–63 characters | yes |
| API base URL | plain HTTPS URL, no query, fragment, or user info; max 180 | yes |
| Device UID | 3–64 lowercase letters, digits, hyphens | yes |
| Device key | exactly 64 hexadecimal characters | yes |
| Device label | 1–160 characters | yes |
| Measurement point | 1–64 lowercase letters, digits, hyphens | yes |

The local portal is HTTP transported inside the WPA2-encrypted setup WLAN. The device key is never written to serial output, application logs, dashboard storage, or URL parameters. The firmware’s normal server connection is always HTTPS and never uses an insecure TLS fallback.

## Configuration after onboarding

The successful credential check returns the current versioned device config. Firmware validates the complete document and persists it as one runtime configuration containing:

- `config_version`
- default measurement interval and effective interval for every active measurement point
- upload interval
- compiled-cap batch size (64 in the reference implementation, even though Protocol V1 permits 500)
- temperature alarm enabled flag and minimum/maximum

The device fetches config during the onboarding check. In normal operation, every successful heartbeat and measurement response also contains the complete current operational configuration; an explicit config fetch remains the fallback and periodic verification path. It replaces the stored configuration only when the response is complete, valid, newer, and durably committed as one unit. Dashboard battery thresholds remain display-only and are not sent to firmware in Protocol V1. WLAN credentials, setup password, and device key are immutable provisioning inputs and are never returned in telemetry responses.

## Recovery and factory reset

Hold the configured factory-reset/BOOT pin low for at least five seconds during boot. The reference firmware clears provisioning credentials, runtime config, sequence state, and all pending measurements, then starts the setup AP again.

This reset is intentionally destructive. Export or upload pending readings before resetting whenever possible. A normal power cycle never clears credentials, sequence state, runtime config, or the durable 64-record pending queue.

## At-rest and production hardening

The prototype stores small values in ESP32 NVS through `Preferences`. The checked-in PlatformIO profile does not by itself enable Secure Boot, Flash Encryption, or encrypted NVS. Production hardware must enable Espressif’s supported Secure Boot/Flash Encryption design and NVS encryption, establish a manufacturing process for the unique setup password, protect the reset path against unauthorized physical use, and define certificate/root-store and OTA rotation procedures.

The embedded trust anchor in this reference is ISRG Root X1, not a leaf certificate. `https://haccp.pow24.org` currently chains to this root. A different API host is accepted only if its hostname matches and its chain validates with the embedded anchor. Update the trust material before its lifecycle ends.

## Reference implementation

The buildable ESP32-S3/SHT45 reference lives in [`firmware/esp32-s3`](../firmware/esp32-s3):

- `ProvisioningPortal`: WPA2 SoftAP, captive redirects, WLAN scan, field validation, verify-before-save flow
- `DeviceState`: NVS provisioning/config, monotonic sequence, boot counter, durable 64-record queue
- `HaccpClient`: verified HTTPS, config, heartbeat, batch upload, exact ACK correlation
- `main.cpp`: SHT45 sampling, local alarm evaluation, reconnect/retry loop, periodic config refresh

It is an awake prototype suitable for bench testing, not yet a power-optimized deep-sleep product firmware. The implementation brief for the next firmware task is [`FIRMWARE_IMPLEMENTATION_HANDOFF.md`](FIRMWARE_IMPLEMENTATION_HANDOFF.md). Hardware validation, battery-divider calibration, manufacturing secrets, Secure Boot/Flash Encryption, OTA, and final enclosure/reset behavior remain release gates.
